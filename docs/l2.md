# L2 support

`android/lib-lm3` is the Android local-link layer. It uses Android framework
APIs for nearby connectivity and publishes/accepts commands through `MsgMux`.

Supported link families in the current code:

- WiFi Direct / P2P
- WiFi scan and network status
- WiFi Aware / NAN, when available
- BLE scan and advertising
- legacy Bluetooth code exists, but `DMService` does not currently subscribe it

The current app does not expose these as a separate AIDL API. Commands are
messages with a `:uri` routed by `MsgMux`.

## Service wiring

`app-dmesh` `DMService` subscribes:

- `wifi` to `LocalMesh`
- `ble` to `LocalMesh.ble`
- `N` to the notification handler
- `I` to the service identity/update handler
- `:open` to initial status publication

This means a command URI beginning with `/wifi/...` or `/ble/...` can be sent
from a local Binder/Messenger client or from the Rust-owned SSH message bridge.

## SSH command shape

Over SSH JSONL, send one object per line:

```json
{"id":"1","method":"wifi.scan","data":{"reason":"manual"}}
```

Rust parses the stream and creates an Android `Bundle`:

- `uri` to Bundle key `:uri`
- `id` to Bundle key `:rid`
- string values under `data` to Bundle string fields

Acknowledgements and errors are written back as JSON Lines. Asynchronous event
streaming back to the SSH client is not currently wired.

If the first character of a line is not `{`, the bridge treats the line as a
human command. Bare words form the URI path, and options become Bundle values:

```sh
wifi scan reason=manual
wifi scan --reason manual
wifi scan --reason=manual
/wifi/scan --id scan-1 --reason manual
```

The examples above map to `/wifi/scan` with `reason=manual`. `id` or `--id`
maps to the response id field.

## Native message shape

Android should use message/pubsub interfaces for Rust modules instead of adding
one JNI method per feature. The current radio protocol JNI path uses:

```text
method: text command name
args: text key/value arguments
data: raw byte[] payload
fd: optional file descriptor slot, -1 when unused
```

This keeps binary radio frames as bytes across JNI and leaves room for future
CBOR frames without changing the Java/Rust boundary. Do not base64 payloads for
local JNI calls, and do not introduce protobuf for this path.

## WiFi commands

Handled by `LocalMesh`.

Start a WiFi/BLE/NAN scan:

```json
{"id":"scan-1","method":"wifi.scan","data":{"reason":"manual"}}
```

Start one WiFi Direct discovery pass:

```json
{"id":"disc-1","method":"wifi.disc"}
```

Control P2P discovery:

```json
{"id":"con-start","method":"wifi.con.start"}
{"id":"con-stop","method":"wifi.con.stop"}
{"id":"con-cancel","method":"wifi.con.cancel"}
```

Connect to a peer discovered by P2P:

```json
{"id":"con-peer","method":"wifi.con.peer","data":{"peer":"PEER_ID","mode":"MODE"}}
```

Update P2P state with parameters:

```json
{"id":"p2p-1","method":"wifi.p2p","data":{"disc":"1"}}
{"id":"p2p-2","method":"wifi.p2p","data":{"ap":"1"}}
{"id":"p2p-3","method":"wifi.p2p","data":{"con":"PEER_ID","mode":"PBC"}}
```

Control advertising:

```json
{"id":"adv-on","method":"wifi.adv","data":{"on":"1","p2p":"1","id4":"test"}}
{"id":"adv-off","method":"wifi.adv","data":{"on":"0","p2p":"0"}}
```

Foreground-service and scheduled-job update windows listen by default. They
start BLE scan and NAN attach/publish/subscribe without taking wake locks.
Advertising is only for wake or pending-data hints.

NAN commands, when Android supports WiFi Aware:

```json
{"id":"nan-ping","method":"wifi.nan.ping","data":{"text":"hello"}}
{"id":"nan-con","method":"wifi.nan.con","data":{"peer":"PEER_ID"}}
{"id":"nan-msg","method":"wifi.nan.msg","data":{"peer":"PEER_ID","text":"hello"}}
```

NAN service-specific info and follow-up messages use the DMesh `DM` v1 binary
layout from the ESP32 firmware protocol. Android owns `WifiAwareManager`
sessions and peer handles; `lmesh::radio_protocol` owns encoding, parsing,
dedupe, and message metadata.

## BLE commands

Handled by `Ble`.

```json
{"id":"ble-scan","method":"ble.scan"}
{"id":"ble-stop","method":"ble.stop"}
{"id":"ble-adv","method":"ble.adv","data":{"text":"hello"}}
{"id":"ble-adv-stop","method":"ble.adv"}
```

BLE scanning and advertising require Android runtime permissions and may be
restricted by background/foreground service policy. DMesh BLE uses 16-bit
service UUID `0xFD5D` service data for wake/discovery hints and Nordic UART
UUIDs for directed GATT payload transfer. BLE scan also registers a
`PendingIntent` scan so framework matches can wake/dispatch to the app without
an app-held wake lock. Android accepts DMesh service-data-only advertisements
from ESP32 firmware as well as advertisements that include the service UUID, and
parses the same `lmesh::radio_protocol` `DM` v1 frame format used for NAN.

## Events

Common published events include:

- `/net/status`: merged visible-device and link status
- `/netif/<ifname>` and `/netip/<ifname>/<addr>`: current network interfaces
- `/wifi/AP`: P2P/AP state
- `/wifi/p2p/discState`: P2P discovery state
- `/wifi/peer/DISC/...`: P2P peer discovery
- `/wifi/BLE/DISC`: BLE discovery folded into WiFi status
- `/BLE/start`: BLE startup information
- `/BLE/DISC`: parsed DMesh BLE v1, Meshtastic, or Nordic UART discovery
- `/BLE/ERR/...`: BLE scan/advertise errors
- `/net/NAN/FollowupRx` and `/net/NAN/FollowupTx`: parsed DMesh NAN v1 follow-ups
- `/net/NAN/...`: WiFi Aware attach, publish, subscribe, and message events

## Manual SSH example

After running `./scripts/build-android.sh ssh-jsonl-smoke` once to generate and install
the test CA/certificate, send JSON:

```sh
printf '%s\n' '{"id":"scan-1","method":"wifi.scan","data":{"reason":"manual"}}' |
timeout 12 ssh \
  -i target/ssh-jsonl-smoke/id_ecdsa \
  -o CertificateFile=target/ssh-jsonl-smoke/id_ecdsa-cert.pub \
  -p 11522 \
  -o StrictHostKeyChecking=no \
  -o UserKnownHostsFile=/dev/null \
  -o ControlMaster=no \
  -o ControlPath=none \
  -o PreferredAuthentications=publickey \
  -o PasswordAuthentication=no \
  dmesh@127.0.0.1 \
  -W dmesh-msg:1
```

Or use the human command form:

```sh
printf '%s\n' 'wifi scan --id scan-1 --reason manual' |
timeout 12 ssh \
  -i target/ssh-jsonl-smoke/id_ecdsa \
  -o CertificateFile=target/ssh-jsonl-smoke/id_ecdsa-cert.pub \
  -p 11522 \
  -o StrictHostKeyChecking=no \
  -o UserKnownHostsFile=/dev/null \
  -o ControlMaster=no \
  -o ControlPath=none \
  -o PreferredAuthentications=publickey \
  -o PasswordAuthentication=no \
  dmesh@127.0.0.1 \
  -W dmesh-msg:1
```

See [debugging.md](debugging.md) for full setup details.

## Live radio tests

Use [debugging.md](debugging.md) for the full manual and automated procedures.
The short forms are:

```sh
scripts/live_android_radio_test.py \
  --device 94AAY0LALC --device RFCNB05AJ7E --auto-serial --duration 12

scripts/live_lora_android_test.py \
  --android 94AAY0LALC --android RFCNB05AJ7E \
  --tx /dev/ttyUSB0 --rx /dev/ttyUSB1 --wait 12
```

Expected Android history for firmware LoRa payload delivery over BLE includes
`BLE.DISC proto=dmesh event=lora_rx`. WiFi Aware/NAN official backend testing
should check for discovery/match first; raw firmware NAN action frames are not
delivered to Android apps as framework follow-up messages.
