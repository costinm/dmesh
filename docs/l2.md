# L2 support

`android/app-dmesh` owns the Android local-link layer. It uses Android
framework APIs for nearby connectivity. Rust owns the command catalog and
routing; Android receives only the selected platform operation or DirectBinder
stream.

Supported link families in the current code:

- Wi-Fi Direct P2P Group Owner, scan, and network status
- WiFi Aware / NAN, when available
- BLE scan and advertising
- legacy Bluetooth code exists, but `DMService` does not currently subscribe it

The current app does not expose these as a separate AIDL API. Apps submit a
typed `MeshStream` through `MeshClient` to app-dmesh; app-dmesh applies Rust
policy before activating another application.

## Service wiring

`app-dmesh` `DMService` translates Rust-selected Wi-Fi, BLE, network, and
DirectBinder operations to Android framework APIs. It does not maintain a Java
subscriber registry or make routing decisions. Shared HTTP and QUIC-lite
services provide the external control ingress.

When `DMService` starts its Rust mesh node, Android also starts the shared IPv6
UDP service on port `3336`. It uses the same bearer-neutral registry as the
host and firmware, including the standard `status`, `handlers`, and `probe`
services; stopping the mesh node aborts that listener with the other native
tasks.

NAN is started immediately with the service and kept attached with both the
connection service (`dmesh`) and the low-rate presence service
(`dmesh-announce`). Android's periodic job is only a repair/presence trigger:
Android permits periodic work no more often than every 15 minutes, and its
actual execution time is inexact. The boot presence record and each periodic
refresh are size-limited tagged-CBOR `announce` records, not an identity claim.
Android forwards every Wi-Fi Aware adapter callback it handles (availability,
attachment/identity, discovery/configuration, session termination, and
follow-up send/receive) into Rust; Rust retains the one-hour peer inventory
used by the status screen. Java keeps only the session-scoped `PeerHandle`
required to invoke framework NAN APIs. The Rust-to-Android bridge invokes
platform handlers without taking ownership of framework sessions.

## SSH message transport

`dmesh-msg:1` is a binary direct stream. Each size-limited message record is prefixed
with a four-byte big-endian length. The native transport only passes record bytes;
`lib-dmesh` exposes `CborMessageCodec` to convert the supported CBOR subset to
the typed `MeshStream`/Bundle projection used by Android apps. SSH exec text
and JSON Lines are not message APIs.

`MeshStreamHandlers` is the shared Android handler registry. Apps can expose
handlers through its DirectBinder adapter and consume them through
`MeshClient`; app-dmesh uses the same registry for its private
`android.keystore` platform handler. JNI sends a handler name and CBOR request
bytes and receives CBOR reply bytes. The keystore handler
accepts `ensure` with `data.challenge` bytes and `sign` with `data.message`
bytes; it returns DER certificate bytes or signature bytes in the reply data.
The private key remains in Android Keystore. This handler is callable only
through Rust's internal platform callback, not as a public mesh method.
`ensure` reuses an existing key; its challenge is applied only on first
creation, and Rust must inspect the returned certificate chain.

`BatteryMonitor` is a local `MeshClient` producer. It sends a CBOR
`battery.state.update` stream to app-dmesh, which admits only its own UID and
passes the record to a private Rust handler. Rust stores the common
`BatteryState`; the read-only `telemetry.battery` method returns that state.

## Native message shape

Android should use message/pubsub interfaces for Rust modules instead of adding
one JNI method per feature. The current radio protocol JNI path uses:

```text
method: text command name
args: text key/value arguments
data: raw byte[] payload
fd: optional file descriptor slot, -1 when unused
```

This keeps binary radio frames as bytes across JNI and leaves room for future
CBOR frames without changing the Java/Rust boundary. Do not base64 payloads for
local JNI calls, and do not introduce protobuf for this path.

## Wi-Fi and NAN controls

Android implements platform Wi-Fi scanning and NAN attachment behind shared Rust
handlers. Use `dmesh-cli` with a reachable `udp://` address for the common
QUIC-lite methods, or forward the HTTP port for Android platform services:

```sh
adb -s SERIAL forward tcp:18480 tcp:18480
dmesh-cli http://127.0.0.1:18480 wifi.scan
dmesh-cli http://127.0.0.1:18480 transport.set --mode=6
dmesh-cli http://127.0.0.1:18480 radio.history --limit=80 --keys=net.NAN,wifi.nan
dmesh-cli udp://[ANDROID_LINK_LOCAL%IFACE]:3336 discovery.nodes
dmesh-cli udp://[ANDROID_LINK_LOCAL%IFACE]:3336 discovery.active
```

`transport.set` replaces the volatile radio profile; it is not a narrow
role toggle. `wifi.scan` can wake the Wi-Fi radio, so avoid repeated fresh
scans. `discovery.active` solicits a time-limited observation window, while
`discovery.nodes` reports Rust's retained inventory. `nan.wakeup` accepts
a target MAC; acceptance alone is not proof the target replied.

Older `wifi.nan.*`, `wifi.adv`, and ad-hoc JSON shell commands were
provider-only experiments and are not current control methods. Android still
owns WifiAwareManager sessions and peer handles; Rust owns the shared
radio protocol and message semantics.

## Android BLE commands

The Android BLE scan and status surface is the shared `ble` HTTP service. Use
`ble.status`, `ble.scan`, `ble.scan_stop`, `ble.scan_results`, and
`ble.scan_clear`. `companion.pair` and `companion.unpair` select the bearer for
the operation with `kind=ble`, `kind=wifi`, or `kind=uart`; ownership itself
works across all available transports. The Android BLE adapter currently
requests a Bluetooth bond and secure L2CAP CoC, while Wi-Fi requires signed
discovery and an existing app-private secret. Secret provisioning and full
device/Bluetooth reset on unpair are not implemented yet; see root `API.md`
for the required lifecycle. The private secret is never returned by HTTP.

BLE scanning and advertising require Android runtime permissions and may be
restricted by background/foreground service policy. DMesh BLE uses two
DMesh-specific 128-bit UUIDs:

- Pairing UUID: `5f6b6f80-4f2a-4a6f-8c42-4d6573680001`
- Operational wake/data UUID: `5f6b6f80-4f2a-4a6f-8c42-4d6573680002`

Android Companion Device Manager pairing scans for the pairing UUID. The normal
BLE wake/discovery scan includes both the operational UUID and the pairing UUID:
operational advertisements are parsed for pending payloads, while pairing
advertisements are logged as `BLE.DISC proto=dmesh_pairing`. When the user
selects Pair companion, Android first claims a recently seen DMesh pairing
advertisement; otherwise it opens a short pairing window. If CDM times out, the
foreground service can still claim the first DMesh pairing advertiser seen by the
normal scanner. Directed GATT payload transfer uses DMesh
service/characteristic UUIDs:

- GATT service UUID: `5f6b6f80-4f2a-4a6f-8c42-4d6573680003`
- RX characteristic UUID: `5f6b6f80-4f2a-4a6f-8c42-4d6573680004`
- TX characteristic UUID: `5f6b6f80-4f2a-4a6f-8c42-4d6573680005`

BLE scan also registers a
`PendingIntent` scan so framework matches can wake/dispatch to the app without
an app-held wake lock. Android accepts DMesh service-data-only advertisements
from ESP32 firmware as well as advertisements that include the service UUID, and
parses the same `dmesh-rawnan::protocol` `DM` v1 frame format used for NAN.

## Shared BLE HTTP service

The common `ble` service is registered in `dmesh-server` and implemented by the
local platform backend. Android registers it first; Linux can register the same
service name with its own BLE backend later.

```sh
curl -sS 'http://127.0.0.1:18480/_m/mesh/services/ble/tools'
curl -sS -X POST \
  'http://127.0.0.1:18480/_m/mesh/services/ble/call/ble.status' \
  -H 'content-type: application/json' -d '{"id":1}'
```

Methods:

| Method | Operation |
| --- | --- |
| `ble.status` | Return local BLE adapter, CoC, and bearer state |
| `ble.scan` | Start a time-limited local scan for DMesh companion advertisements |
| `ble.scan_stop` | Stop the local scan without clearing retained results |
| `ble.scan_results` | List retained scan results, optionally with `limit` |
| `ble.scan_clear` | Clear retained scan results |
| `companion.pair` | Begin the BLE bond and secure CoC path with `kind=ble`, scanned `id`, and optional `psm`; full device provisioning is pending |
| `companion.unpair` | Currently release the local BLE bearer selected by `kind=ble` and `id`; device and bond reset is pending |

`ble.scan_results` retains at most 32 Rust-side entries keyed by address. Each
entry contains `address`, `rssi`, `service_data`, and `last_seen_ms`.

The shared `transport` service exposes the portable `transport.set` method. It
accepts `wake_target`, `mode`, `ap`, `now`, `ble`, and `nan_dw_interval`. For
the sleepy-e8 wake case, use `mode=6`, `ap=1`,
`now=1`, `nan_dw_interval=1`, and `ble=1` or `ble=2`. Android sends the
parameterized record as a targeted NAN active-subscribe `wake_request`; the
target applies the requested active radio profile and BLE selector.
`wake_target` is the target's STA or AP radio MAC, not its BLE address.

```sh
curl -sS -X POST \
  'http://127.0.0.1:18480/_m/mesh/services/transport/call/transport.set' \
  -H 'content-type: application/json' \
  -d '{"id":2,"wake_target":"10:BD:A3:AC:5A:20","mode":6,"ap":1,"now":1,"ble":1,"nan_dw_interval":1}'
```

The DMesh-owned HTML companion page is extracted to the app private `web`
directory and served by the admin web root:

```text
/_m/adm/ble.html
```

## Shared USB HTTP service

The common `usb` service is registered in `dmesh-server` and implemented by the
Android USB Host backend. It opens an ESP32 or USB-UART bridge attached to the
phone, claims its first bulk-capable serial interface, and routes bytes through
the same Rust bearer runtime as BLE. USB/UART ingress and egress use PPP/HDLC
with the `0xF7` QUIC-lite transport marker. BLE L2CAP CoC instead maps one
QUIC-lite packet to one CoC SDU.

```sh
curl -sS 'http://127.0.0.1:18480/_m/mesh/services/usb/tools'
curl -sS -X POST \
  'http://127.0.0.1:18480/_m/mesh/services/usb/call/usb.status' \
  -H 'content-type: application/json' -d '{"id":1}'
curl -sS -X POST \
  'http://127.0.0.1:18480/_m/mesh/services/usb/call/usb.open' \
  -H 'content-type: application/json' -d '{"id":2,"auto":true}'
```

| Method | Operation |
| --- | --- |
| `usb.status` | Return USB host, serial adapter, and Rust bearer state |
| `usb.devices` | List devices visible to the Android USB Host |
| `usb.open` | Open a USB serial device; `vendor_id` and `product_id` select one explicitly, otherwise auto-discovery opens an eligible Espressif bulk device |
| `usb.close` | Close the active USB serial bearer |

Android auto-attaches when an eligible Espressif USB device (vendor `0x303a`
with a bulk in/out interface) is present and the app already has USB
permission. Auto-discovery and auto-attach are Espressif-only; other devices,
such as generic CDC-ACM adapters or USB-UART bridges, are reachable only by
passing an explicit `vendor_id` and `product_id` to `usb.open`. If permission
has not been granted, the system permission dialog is shown for
`com.github.costinm.dmesh.lm.USB_PERMISSION`; while that dialog is up,
`usb.open` answers `status: pending`, not `rejected`. Feasibility: CDC-ACM and
Espressif USB-Serial-JTAG devices are openable through the same bulk endpoint
path when Android exposes them; GPIO UART is not a USB device and requires a
USB-UART bridge. For C6 USB-Serial-JTAG, attach the USB host before the ESP
boots or reboot it while attached, because the current firmware selects
USB-JTAG at boot rather than switching from GPIO UART at runtime.

In single-companion mode, Android stores at most one ESP association. The ESP
advertises only when it has pending data. Android wakes from the BLE scan or
companion presence callback, connects as the BLE central, subscribes to DMesh
TX notifications, writes `ready max_bytes=1200 after_seq=N`, and the firmware
pushes text-framed messages with raw byte payloads:

```text
msg seq=18 hash=43a1c7a7 len=512
<512 raw bytes>
done count=1
```

Android appends received payloads to
`files/radio/ble/messages.bin` and ACKs each saved payload with
`ack seq=18 hash=43a1c7a7`. Firmware should delete a queued message only after
that ACK.

Companion association is started from the app UI. Stored BLE payload state is
an app-private diagnostic artifact, not an ADB shell command surface. Use the
`ble` HTTP service for scripted scan and CoC connection control.

## Main BLE tagged commands

`fw/main` exposes a separate numeric tagged component for the Main-owned NimBLE
radio. It is not the Android text `ble.*` command surface.

Component `104` methods:

| Method | Operation |
| ---: | --- |
| 80 | Start BLE advertising and the L2CAP CoC server |
| 81 | Stop scan and advertising, then terminate the active LE connection if present |
| 82 | Start a time-limited passive scan; optional field `2` is duration in ms |
| 83 | Return BLE status |
| 84 | Stop the active scan |
| 85 | Start a central GAP connection and CoC channel; fields are `2 addr` bytes, `3 addr_type`, and optional `4 psm` |
| 86 | Send one CoC SDU; field `2 data` is hex bytes |

The Main advertisement includes flags `0x06`, complete UUID16 list `0x1820`,
and complete UUID128 list `5f6b6f80-4f2a-4a6f-8c42-4d6573680001`. Pairing is
Just Works with bonding enabled; bonds persist through `CONFIG_BT_NIMBLE_NVS_PERSIST=y`.
The CoC server uses PSM `0x0080`. Each CoC SDU is one opaque QUIC-lite packet
and is injected into the shared Main connection path with bearer ID `7` and a
zero peer source.

`status` returns a fixed-size map:

| Field | Meaning |
| ---: | --- |
| 1 | `ready` |
| 2 | `advertising` |
| 3 | `connected` |
| 4 | `coc_connected` |
| 5 | `generation` |
| 6 | `handle` |
| 7 | `coc_rx` |
| 8 | `coc_rx_rejected` |
| 9 | `scanning` |
| 10 | `scan_reports` |
| 11 | `scan_matches` |
| 12 | `last_scan_addr`, 6 bytes |
| 13 | `last_scan_addr_type` |
| 14 | `last_scan_rssi` |
| 15 | `bonded` |
| 16 | `coc_tx_pending` |
| 17 | `local_addr`, 6 bytes |
| 18 | `local_addr_type` |

## Android transport.set

`transport.set` is the shared `dmesh-server` control request. Its canonical
wire representation is tagged CBOR control method `1/4`; Android Bundles are
typed edge projections, not JSON command APIs.
Use an `id` for a correlated operation. `mode` is `nan` or `sta`; optional
fields are `ssid`, `passphrase`, `bssid_hex`, `channel`, `ap`, `open`, `ndp`,
`now`, `nan_dw_interval`, the STA/raw-radio tuning fields, and `uart`.

```sh
adb -s SERIAL forward tcp:18480 tcp:18480
dmesh-cli http://127.0.0.1:18480 transport.set --mode=6 --ap=1
```

`wifi.transport.start` and the old JSON envelope are retired aliases. Android
currently applies STA credentials/channel and NAN/P2P group selection. Raw
ESP-NOW/STA tuning, UART, NDP, and an unauthenticated Android P2P group are
represented by the common request but are not Android controller features yet;
adapters must report those capabilities rather than silently reinterpret them.

For a successful Android P2P Group Owner, the response contains
`state=started`, the configured `DIRECT-*` `ssid`, and its WPA2
`passphrase`. Use `ap=0` with a new request id to remove the group. Completion
waits for Android's P2P disconnect action and a `requestGroupInfo()` result
with no group; a release timeout is an error, not a successful mode change.
While a
P2P group owns the radio, Android may terminate Wi-Fi Aware; DMesh therefore
advertises the same size-limited CBOR `transport.set` record through Wi-Fi Direct
DNS-SD with instance `dmesh`, service type `_dmesh._tcp`, and TXT key `cbor`
(lower-case hexadecimal). This is a radio envelope change only: receivers
decode the TXT value and pass the original CBOR to the normal control decoder.
ESP32 and Linux P2P SD receive/decode remain the next interoperability step.

Common published events include:

- `/net/status`: merged visible-device and link status
- `/netif/<ifname>` and `/netip/<ifname>/<addr>`: current network interfaces
- `/wifi.p2p.group`: P2P Group Owner lifecycle and volatile credentials
- `/net.P2P.ServiceInfo`: P2P DNS-SD CBOR advertisement state
- `/wifi/BLE/DISC`: BLE discovery folded into WiFi status
- `/BLE/start`: BLE startup information
- `/BLE/DISC`: parsed DMesh BLE v1 or Meshtastic discovery
- `/BLE/PENDING`: Android saw pending companion data and will connect/probe
- `/BLE/PULL`: BLE GATT pull/push state, including subscribe, ready, ACK, done
- `/BLE/MSG`: one raw payload was appended to `messages.bin`
- `/COMPANION/...`: association and presence state
- `/BLE/ERR/...`: BLE scan/advertise errors
- `/net/NAN/FollowupRx` and `/net/NAN/FollowupTx`: parsed DMesh NAN v1 follow-ups
- `/net/NAN/...`: WiFi Aware attach, publish, subscribe, and message events
- `/wifi/transport/result`: correlated `transport.set` completion, including
  P2P credentials only for the requesting privileged control plane

## SSH message transport

`dmesh-msg:1` carries length-prefixed opaque message records, not JSON Lines
or shell text. The SSH layer forwards bytes; `dmeshnative` maps the payload to
the typed Bundle contract before application dispatch. See
[debugging.md](debugging.md) for setup and the shared control surface.

## Live radio tests

Use [debugging.md](debugging.md) for the full manual and automated procedures.
The short forms are:

```sh
scripts/live_android_radio_test.py \
  --device 94AAY0LALC --device RFCNB05AJ7E --auto-serial --duration 12

scripts/live_lora_android_test.py \
  --android 94AAY0LALC --android RFCNB05AJ7E \
  --tx /dev/ttyUSB0 --rx /dev/ttyUSB1 --wait 12
```

Expected Android history for firmware LoRa payload delivery over BLE includes
`BLE.DISC proto=dmesh event=lora_rx`. WiFi Aware/NAN official backend testing
should check for discovery/match first; raw firmware NAN action frames are not
delivered to Android apps as framework follow-up messages.
